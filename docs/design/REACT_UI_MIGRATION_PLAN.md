# React 프론트엔드 전환 계획

작성: 2026-10-19 · 상태: Docker·조회 API 통합 검증 완료, 브라우저 시각 검증 대기

## 목표와 범위

FastAPI·LangGraph·SQLite를 유지하면서 Streamlit UI를 React 운영 화면으로 단계적으로
전환한다. 핵심 흐름은 이벤트 선택 → 설비 정보를 전달한 진단 → 작업지시서 검토 →
승인/반려 → CMMS 전송 결과·감사 확인이다. 이번 작업은 기존 저장소의 로컬 구현이며
외부 사이트 게시나 실제 승인·Slack·CMMS 전송을 검증에 사용하지 않는다.

기존 `UI_UPGRADE_PLAN.md`는 이전 Streamlit 개선 완료 기록으로 보존한다.

## 전환 전 현황

- `frontend/streamlit_app.py`: 약 1,200줄, 설비 에이전트·매뉴얼·이벤트·재고·감사 5탭.
- API는 `backend/main.py`에 분리되어 있다. 진단은 동기 POST이며
  `/agent/status/{thread_id}`로 running/pending_approval/done/failed/not_found를 조회한다.
- 승인 상태는 SQLite 체크포인트에 남지만 전체 승인 대기 목록 API는 없다.
- 이벤트는 설비별 최신 1건이며 `/events`는 limit 조회만 지원한다.
- 설비 목록·상세·센서 시계열 API는 없다. 작업지시서는 문자열이다.
- 서버 CORS는 8501만 허용한다. React는 개발·배포 모두 `/api` 프록시를 사용한다.

## 기술과 배치

- React + TypeScript + Vite, React Router, TanStack Query.
- Tailwind CSS, shadcn 방식의 로컬 UI 컴포넌트와 Radix 확인 대화상자, Lucide 아이콘.
- 차트는 설비 시계열 API 도입 시 Recharts 추가. 현재 없는 데이터는 만들어 표시하지 않는다.
- `frontend/web/`에 신규 UI를 격리한다. 기존 Streamlit과 기본 Compose는 유지한다.
- 별도 Compose 파일로 Node 빌드 → Nginx 정적 제공 → `/api/` FastAPI 프록시를 제공한다.
- 번들에 외부 CDN·원격 폰트·API 비밀키를 포함하지 않는다.

## 보존할 의미와 오류 동작

- 위험 점수는 보정된 고장 확률이 아니다. 조회 실패·빈 결과를 정상으로 표현하지 않는다.
- 이벤트 완료는 목록 정리이며 정비 완료 기록을 만들지 않는다.
- 재고·리드타임은 합성, 수요는 추정, 발주 대기 물량은 미반영임을 표시한다.
- 실제 조회 시각·데이터 기준 시각·이벤트 근거 시각·감사 시각을 구분한다.
- 3개 AI 관점은 근거 확인 없이 생성된 참고 의견이다.
- 승인 결과와 외부 전송 결과는 분리한다. sent/partial_tasks/creation_unknown/
  미설정/오프라인 차단을 서버 응답대로 표시한다.
- 진단 POST는 재시도하지 않는다. 타임아웃/5xx/연결 실패는 결과 미확인으로 두고
  같은 thread_id의 상태를 조회한다. 승인 POST 역시 자동 재시도하지 않는다.
- 진행 중 화면을 닫아도 서버가 취소되지 않는다. URL로 다시 열 수 있게 한다.
- localStorage에는 진단 내용·작업지시서·개인정보를 저장하지 않는다.

타입 검사와 production build, 부작용 없는 mocked API 기반 UI 테스트로 진단 요청

### Docker 재빌드 후 연동 검증 (2026-10-19)

- 사용자가 재빌드한 백엔드가 healthy임을 확인했다. 새 설비 목록/시계열/승인 대기/
  이벤트 조회가 실제 Docker DB에서 HTTP 200으로 응답했다.
- 설비 100대, 승인 대기 18건, 감지 이벤트 0건을 조회했다. 기존 승인 1건을 상태 조회로
  다시 열어 pending_approval과 원문 보존을 확인했다. 진단·승인·스캔·전송은 실행하지 않았다.
- 데이터 기준 시각은 2026-10-08 09:00:00이며 조회 당시 실제 시각과 약 264시간 차이가
  있었다. 데이터셋 정렬과 실제 최신성의 차이를 실제 응답에서도 확인했다.
- 3000 포트가 다른 앱에 사용 중이어서 React 기본 Docker 포트를 3001로 변경했다.
  `UPTIME_WEB_PORT`로 바꿀 수 있다. 기존 앱과 백엔드를 재시작하지 않고 web만 빌드·실행했다.
- `http://127.0.0.1:3001/`, `/machines/1`, `/approvals`와 JS/CSS 정적 파일 HTTP 200.
- 3001의 `/api/health`, 설비 목록, 72시간/3시간 집계, 승인 대기, 이벤트 필터 HTTP 200.
  `nginx -t`도 통과했다. 별도 창 새로고침에 필요한 SPA 경로 응답을 확인했다.
- 실제 브라우저 렌더링·키보드·모바일 검증과 쓰기 동작을 포함한 전체 시나리오는 남아 있다.

### 진단 모델 설정 복원 (2026-10-19)

- 사용자 진단 실패의 Docker 로그에서 `Unrecognized request argument supplied: reasoning_effort`를
  확인했다. 로컬 `.env`와 실행 컨테이너 모두 `OPENAI_MODEL=gpt-4o-mini`였다.
- 사용자 요청에 따라 `.env`의 모델만 `gpt-5.6-luna`로 복원하고 백엔드 컨테이너를
  재생성했다. 호환성 필터 코드나 API 키는 변경하지 않았다.
- OpenAI Models 조회에서 `gpt-5.6-luna` 접근 가능, `/health`에서 모델 반영 및 정상 상태를
  확인했다. React Nginx 프록시도 갱신했다.
- 실패한 기존 진단은 자동 재실행하지 않았다. 실제 진단 생성의 성공 여부는 새 요청으로
  확인해야 하며, 이번 확인은 모델 접근과 설정 반영까지다.
- 공식 지원 범위: https://developers.openai.com/api/docs/models/gpt-5.6-luna

### 일반 진단의 외부 연동 안내 수정 (2026-10-19)

- 모델 복원 후 사용자가 설비 #64 진단 결과 반환을 확인했다.
- 작업지시서가 없는 일반 진단에도 CMMS 전송 결과가 누락된 것처럼 표시하는 UI를 수정했다.
  일반 진단은 전송 대상 없음, 주의는 자동 전송 대상 아님, 반려는 전송하지 않음으로 표시한다.
- 서버의 실제 전송 상태가 있으면 이를 우선한다. 승인된 긴급 건에서 전송 상태가 없으면
  계속 감사 로그 확인을 안내하며 전송 성공/미전송을 추정하지 않는다.
- 프론트 회귀 테스트 21개와 타입 검사·production build 통과. 진단·승인·전송 요청은
  검증에서 재실행하지 않았다.
