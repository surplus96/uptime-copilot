# 자동 감지 시뮬레이터 계획 (브랜치 `workspace-mac-2`)

> 런타임 테스트 흐름 중 "이벤트 생성 → 스캔 → Slack 알림" 구간을 실제 제조 시스템의
> 알람 구조에 맞게 자동화한다. 이후 구간(에이전트 탭 조회 → 사람 승인 → CMMS 등록)은
> 사람이 하는 단계로 그대로 둔다. 이 문서는 설계 기록이며, 구현 상태는 맨 아래
> "진행 상태"에 갱신한다.

## 현재 흐름과 목표 흐름

| 단계 | 현재 | 목표 |
|---|---|---|
| 이벤트 생성 | FastAPI docs에서 `POST /simulate/tick` 수동 호출 | 백그라운드 루프가 자동 생성 |
| 이벤트 확인 | 이상감지 탭의 스캔 버튼 수동 클릭 | 틱마다 자동 스캔 + 탭 자동 갱신 |
| Slack 알림 | 스캔 시 발송 | 스캔당 새 감지 건을 한 메시지로 묶어 발송 |
| 조회·승인·CMMS | 사람 | 그대로 |

## 현재 `generate_tick()`의 한계 (`backend/data/event_simulator.py`)

- **상태 없음**: 호출마다 5% 확률로 이상 설비를 새로 뽑아서 열화가 이어지지 않는다.
- **계단식 이상**: 이상이 걸리면 배치 전체에서 4~6σ 편차가 고정된다(점진적 열화 아님).
- **오류 폭주**: 이상 설비는 시간마다 오류 이벤트를 만든다.
- **수동 트리거**: 틱과 스캔을 각각 사람이 실행한다.
- **비용**: `detect_anomaly()`가 스캔마다 설비의 전체 텔레메트리를 읽고, 시뮬레이터도
  틱마다 전체 테이블로 기준선을 다시 계산한다.

**알려진 편차(2026-09-22 기준, 독립 확률 오류였을 때)**: 실제 데이터는 "오류가 이후 168h 내
고장으로 이어지는 비율"이 35.5%인데 시뮬레이션은 약 56%였다. 2026-10-01에 전조 오류를 서명
방식으로 바꾸면서 이 비율은 다시 재지 않았다.

**데모용 예외**(Z-score 폴백 기준 — 모델이 있을 때의 주의는 아래 2026-10-01 절): 실제로는 3σ 이상
열화가 1.2%뿐이라 텔레메트리 Z-score 기반 **주의** 감지가 거의 발생하지 않는다. 데모에서 주의 경로가 보이도록 `STRONG_FRACTION`(기본 0.15)만큼은
3.2~4.5σ의 강한 열화로 만든다. 실제 수치보다 높게 잡은 값이며, 0으로 두면 실제 분포다.

## 설비 상태 머신

```
HEALTHY → DEGRADING → FAULT → (고장 + 정비, 06시) → HEALTHY
```

| 상태 | 동작 |
|---|---|
| HEALTHY | 매 시간 `P_EPISODE` 확률로 DEGRADING 진입을 시도한다. 신호 1개를 뽑고, 그 신호 부품이 `START_MIN_AGE_H`(comp1·3·4 1080h / comp2 720h)보다 어리면 시작하지 않는다. 시작하면 방향, 편차 크기, 리드 시간을 확정. 정상 설비는 정기 정비 사건(`_preventive_maintenance`)도 받는다 |
| DEGRADING | 편차가 6시간에 걸쳐 목표 크기까지 오르고 유지. 고장 정확히 24h 전에 그 부품의 서명 오류를 낸다(조용한 고장은 안 냄) |
| FAULT | 서명 오류가 나온 상태(편차 유지) — `P_PRECURSOR_ERROR`가 0이라 들어가는 길은 이것뿐이다. 조용한 고장(`_is_silent`)은 FAULT를 거치지 않고 DEGRADING에서 바로 고장난다. 리드 시간이 지난 뒤 06시에 고장 + 정비 기록(`_failure_companion`이 46% 확률로 다른 부품 하나도 같이 정비) |

- 고장이 나면 부품을 교체한 것으로 보고 바로 HEALTHY로 복귀한다(실제 데이터의 정비 시차 0h).
- 모든 상태에서 고장과 무관한 **배경 오류**가 발생한다(대부분의 오류는 고장으로 이어지지 않음).
- **일시 스파이크**: 상태와 무관하게 시간당 0.5% 확률로 1시간짜리 +4σ. 24시간 평균에서
  약 0.17σ로 희석되어 감지되면 안 되는 오탐 검증용이다(데이터 근거가 아닌 강건성 테스트용).
- 난수는 `random.Random(seed)` 인스턴스를 쓴다(`SIM_SEED`로 재현).
- 이 구조에서 **긴급**은 고장 기록 직후(스캔의 `within_days=1`)에 잡히는 사후 판정이고,
  **주의**는 위험도 모델이 서명 오류와 편차에 반응할 때 잡힌다(대부분 고장 24h 전). 텔레메트리
  Z-score만으로는 약한 열화가 안 잡힌다(실제와 같은 난이도).

검증(2026-09-22, 스크래치에서 2년 × 100대 시뮬레이션, seed 고정. 오류 종류와 방향 부분은 2026-10-01 보정으로 대체됨): 고장 설비당 연 7.2회(실제 7.6),
고장 시각 전부 06시, 오류 종류 분포와 방향 비율이 실제와 일치, 고장 전 168h 내
오류 96%(실제 98%).

## 열화 → 주의 → 긴급 순서 보정 (2026-10-01)

**발견한 문제**: 브라우저 테스트에서 열화 설비 #46/#84가 주의 없이 바로 긴급이 됐다. 주의는 위험도
모델이 경보를 낼 때만 붙는데(`agent_service._diagnose_machine`), 시뮬레이터의 열화 패턴에 모델이
반응하지 않았다. `backend/ml/sim_alarm_eval.py`로 신호별 열화 에피소드를 메모리에서 돌려
(실제 모델 파일 사용, 서버·DB 미접촉) "고장 전에 경보가 뜨는 비율"을 쟀다.

| 신호 | 보정 전(30건, seed 1) | 1차: 전조 오류를 서명으로 | 2차: 열화 방향·크기를 신호별로 (30건) | 같은 설정 100건, seed 2 |
|---|---|---|---|---|
| volt | 53% | 87% | 100% | 100% |
| rotate | 0% | 33% | 100% | 100% |
| pressure | 13% | 47% | 97% | 98% |
| vibration | 3% | 60% | 100% | 100% |

(경보가 매시간 확인된다고 본 값. 라이브처럼 시뮬레이션 12시간마다만 스캔하면 100건 기준
volt 98 / rotate 100 / pressure 96 / vibration 99%. **3차 보정 전의 수치다 — 현재 값은 아래 3차 측정: 83/99/86/94%.**)

**원인(원본 고장 집계 — DB `failures` 764행 = CSV 761건 + 예전 수동 틱 3건 포함, 재집계 안 함)**
1. 고장 직전 오류가 **부품별 서명**을 가진다: comp1←error1, comp2←error2+error3, comp3←error4,
   comp4←error5. 오류의 88%가 고장 24~36시간 전(대부분 정확히 24시간 전)이다. 예전 시뮬레이터는
   시간당 5% 확률로 신호 번호와 같은 오류를 냈다(비율 64%) — 이는 모델이 학습한 패턴이 아니었다.
2. 열화 편차의 **방향이 신호마다 고정**이다(고장의 100%): volt +1.28σ, rotate −1.46σ, pressure
   +2.10σ, vibration +1.80σ(고장 직전 24시간 평균의 z값). 예전엔 방향을 66% 확률로 무작위로 뽑았고
   이 66%는 신호를 합쳐 센 값이라 신호별 방향 정보를 잃은 것이었다. 모델은 이 방향에 반응해서,
   rotate가 올라가는 열화는 경보 0%, pressure가 내려가는 열화도 경보가 안 났다.

**바꾼 것**: `sim_engine.py`의 서명 오류(`SIGNATURE_ERRORS`, `hours_until_failure`로 고장까지 남은
시간을 저장된 상태만으로 다시 계산해 시점을 맞춘다 — `sim_state`에 열을 더하면 기존 DB 마이그레이션이
필요해서 피함), 신호별 방향·크기(`SIGNAL_DIRECTION`, `SIGNAL_DRIFT_MEAN`), 잡음 오류 비율
`P_PRECURSOR_ERROR`(0.05→0.007, 3차에서 0), `inject()`가 같은 방향 표를 쓰도록. 회귀 테스트는
`tests/test_sim_engine.py` 아래쪽 — 기대값은 코드 상수와 별개로 테스트에 다시 적었다(표가 틀려도
통과하는 것을 막으려는 것).

**알려진 한계와 해석 주의**
- 시뮬레이터가 모델과 같은 데이터셋의 패턴을 따르도록 맞춘 것이라, 이 수치는 "시뮬레이터가 모델과
  일관된다"를 보일 뿐 현장에서 모델이 경보를 낸다는 증거가 아니다.

  **원래 가설의 정정**: 앞서 "모델이 어린 부품에는 경보를 안 낸다(모델의 약점)"고 썼는데 틀렸다. 실제 고장 740건을
  고장 23시간 전에 재생하면 600~900시간 구간 78건을 포함해 **99.7%가 경보**를 낸다(2015년 전체 — 학습 구간(1~8월)이 섞여 있어 낙관적일 수 있다. **시험 구간(11~12월)만 재생해도 121건 중 99.2%, 600~900시간 14건 모두 경보**, 경보가 맞는 부품을 가리킨 비율은 94%로 시뮬레이션의 100%보다 낮다. 오경보: 정상 설비 3000시간
  표본 0건, 시뮬레이션 정상 설비 4700표본 0건 — 배경 오류율을 실제로 올려도 0건). 어린 부품의 열화가 안 잡힌
  것은 시뮬레이터가 실제 데이터에 없는 상황(어린 부품의 고장, 서로 독립인 부품 나이)을 만들어서 모델이 본 적 없는
  입력이 됐기 때문이다. 정비 사건 과정으로 부품들이 같은 사건을 공유하게 했더니 독립 나이일 때 volt·pressure
  경보율이 77~81%이던 것이 올라갔다(같은 나이로 묶으면 95~96%까지).
  **측정(`ml.sim_alarm_eval`, 신호별 150건, seed 2, 12시간 틱, 서명 없는 조용한 고장 포함)**:
  volt 83 / rotate 99 / pressure 86 / vibration 94%(매시간 확인하면 87/99/89/98%), 경보가 가리키는 부품은 4개
  신호 모두 100% 일치. **이전 측정(decisions.md 2차 수정, 98/99/98/92%)보다 낮아졌다 — 더 정확해진 시뮬레이터가 이전의 낙관적인
  설정(실제에 없는 나이 분포)을 걷어냈기 때문이다.** 실제 고장 재생(99.7%)과의 남은 차이(volt·pressure 약
  15%p)는 두 가지로 확인했다: ① 실제 부품 나이를 대입하면 91~93%까지 올라가고, 실제 정비·고장이 **15일(360시간)
  달력 격자**(06시)에 몰려 있는데(고장 직전 부품 나이의 대부분이 360의 배수) 시뮬레이터는 격자가 없다 —
  나이를 360시간 격자로 맞추면 +8%p; ② 실제 텔레메트리·오류 피처를 대입하면 86~88%. 격자(설비별 정비·고장 위상)와
  텔레메트리의 미세 구조(자기상관 0.06~0.17, pressure 첨도 0.8 — 시뮬레이터는 독립 정규)까지 맞추는 것은
  이번에 하지 않았다.
  **측정 방식의 한계**: `ml.sim_alarm_eval`은 라이브와 달리 에피소드 중에 정기 정비·고장 동반 정비를 돌리지 않고, 부품 나이를 열화 부품의 하한을 만족하는 한 번의 `draw_initial_ages` 추출로 정한다(라이브의 정상 상태가 아니다). 근사다.
  **정상 설비의 오경보**: 위험 모델이 정상 설비에서 경보를 내지 않는 것은 실제(0/3000)·시뮬레이션(0/4700) 모두
  확인했다.
  **한계**: 부품 나이는 사건 과정의 지수 근사라 상위 구간이 실제보다 10~17% 젊다(300/600/900/1200/1800/3000시간
  분위수가 288/558/820/1079/1563/2482). `estimate_next_maintenance`는 병합·정렬한 모든 정비 기록의 `diff().mean()`을 쓰므로 평균 간격이
  (마지막 − 처음)/(n−1)로 환원돼 심은·정기 정비 기록(2026년)과 원본(2016년) 사이의 약 10년이 평균 간격에 들어간다 —
  코드상 확정이고 실행으로는 확인하지 않았다(고장 정비 기록으로 이미 있던 현상). 정기 정비는 열화·전조 상태의 설비에는 하지 않는다
  (정비하면 고장이 안 날 텐데 그 효과는 모델링하지 않음). `inject()`는 해당 부품이 하한보다 어리면 마지막
  정비 기록을 하한 나이로 당긴다(데모 주입은 "이 부품은 노후했다"는 가정이다).
- **오류-부품 매핑(2026-10-01 후속 일부 반영)**: 모델이 학습한 실제 서명은 comp2←error2+3, comp3←error4,
  comp4←error5인데 앱의 가상 매뉴얼은 error1~4를 같은 번호 부품에 대응시키고 error5를 "복합 이상"으로
  설명한다. 브라우저 테스트에서 comp4 주의 건의 증상에 경보를 일으킨 error5가 빠지고 "매뉴얼 근거"가
  발생하지 않은 error4를 인용하는 것이 확인돼, **error5만 comp4에 연결**했다
  (`rag/pump_manual.ERROR_TO_COMPONENT`; error5 설명은 `data/pdm_operations.py`의 `ERROR_DESCRIPTIONS`에
  "진동 저감 장치 고장 전조로 가장 자주 관측" 추가). 사용자가 선택한 최소 범위다: RAG 매뉴얼 문서와 `ERROR5_NOTE`("복합 오류는 단일 부품 아님")는
  그대로라서 서로 약간 어긋난다. **남은 불일치**: 압력 열화(comp3)는 error4를 내는데 앱은 error4를
  "진동 이상"(comp4)으로 매핑하고, comp2의 error3은 comp3으로 매핑된다 — 원본 데이터를 진단할 때도
  있던 불일치이고 가상 시나리오의 오류 의미를 다시 쓰는 일이라 보류(전면 정합은 RAG 인덱스 재생성과
  테스트·문서 영향이 커서 선택하지 않음).
- 이 보정은 열화→주의 순서를 "대부분" 보이게 할 뿐 보장하지는 않는다(측정상 83~99%, 조용한 고장 1~5% 포함).

## 테이블

원본(`telemetry`, `errors`, `failures`, `maint`)은 읽기 전용으로 두고, 같은 컬럼 구조의
시뮬레이션 테이블을 추가한다.

- `sim_telemetry(datetime, machineID, volt, rotate, pressure, vibration)`
- `sim_errors(datetime, machineID, errorID)`
- `sim_failures(datetime, machineID, failure)`
- `sim_maint(datetime, machineID, comp)`
- `sim_state(machine_id PK, state, signal, direction, drift_sigma, lead_hours, elapsed, errors_emitted)`
- `sim_control(key PK, value)` — `running`, `sim_now`, `hours_per_tick`

각 시뮬레이션 테이블에는 `(machineID, datetime)` 인덱스를 둔다. 시뮬레이션 초기화는
이 테이블들을 비우는 것으로 끝난다.

## 원본 + 시뮬레이션 통합 조회 (누락되면 에이전트 탭이 시뮬레이션 이벤트를 못 봄)

| 대상 | 변경 |
|---|---|
| `pdm_telemetry.detect_anomaly()` | 기준선은 원본에서만 계산해 캐시, 최근 구간은 `sim_telemetry` 우선 |
| `pdm_operations.get_recent_errors()` | 원본 + `sim_errors` 합쳐서 조회하되 기준 시각 30일 이내만(고장 기록 여부와 무관 — 2026-10-01) |
| `pdm_operations.check_recent_failure()` | 원본 + `sim_failures` 합쳐서 조회 |
| `pdm_operations.estimate_next_maintenance()` | 원본 + `sim_maint` 고려 |
| `event_store._dataset_now()` | 원본과 시뮬레이션 텔레메트리 중 최댓값 |
| 기존 `POST /simulate/tick` | ~~새 시뮬레이션 테이블에 쓰도록 통합~~ → **삭제로 결정**(아래 "배포 전 전체 점검" 절 참고) |

알고 있어야 한다.

## 백그라운드 루프와 API

- FastAPI lifespan에서 asyncio 태스크를 띄워 `SIM_TICK_SECONDS`(기본 60)마다
  `SIM_HOURS_PER_TICK`(기본 1)시간을 진행한다. 상태는 `sim_control`/`sim_state`에 저장.
- 틱 직후 **증분 스캔**: HEALTHY가 아닌 설비 + 이번 틱에 이벤트가 생긴 설비만 진단.
  기존 `evidence_at` 중복 방지 로직을 그대로 사용한다.
- Slack은 스캔 1회에 새로 감지된 건을 한 메시지로 묶는다(기존 건별 발송 + 1초 sleep 대체).

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/simulator/start` | 루프 시작 (현재 `sim_state` 그대로 이어감 — 자동으로 지우지 않음) |
| POST | `/simulator/stop` | 루프 정지 |
| GET | `/simulator/status` | 실행 여부, 시뮬레이션 시각, 속도, 열화 진행 목록, `has_stale_events` |
| POST | `/simulator/inject` | 특정 설비를 강제 열화(데모용) |
| POST | `/simulator/reset` | 아래 "클린 상태 보장" 참고 |

## 클린 상태 보장 (2026-09-22 추가)

**발견한 문제**: 시뮬레이션은 "고장 설비 없는 클린 상태에서 시작"을 전제로 설계됐는데
(1번 단계의 `MachineSim`은 전부 HEALTHY로 시작), 실제로는 이전 수동 테스트로 생긴
잔재 데이터가 이미 존재한다 — `event_store.detected_events`에 실제로 3건
(`설비 #5 주의`, `#34/#84 긴급`, 2026-09-18 수동 `/scan` 테스트로 생성)이 남아 있는 걸
직접 확인했다. 자동 시뮬레이터가 새로 돌기 시작해도 이 이벤트들은 사라지지 않고
이상감지 탭에 계속 떠서, 시뮬레이터가 감지한 것처럼 보이는 혼선이 생긴다.

**결정(2026-09-22)**: 자동 리셋은 하지 않는다. `/simulator/start`는 항상 현재
`sim_state`를 그대로 이어간다(서버 재시작 후 진행 유지라는 기존 설계와 일관됨).
잔재 정리는 사용자가 `/simulator/reset`을 **명시적으로 호출**해야만 일어난다 —
자동 삭제로 인한 데이터 유실을 피하기 위함.

**`/simulator/reset`이 지우는 범위** (전부, 부분 리셋 없음):
- `sim_state` → 100대 전부 HEALTHY로
- `sim_telemetry` / `sim_errors` / `sim_failures` / `sim_maint` → 전부 삭제
- `event_store.detected_events` / `completed_events` → 전부 삭제 (원본 여부와 무관하게
  "현재 열려 있는 알람" 전체를 지운다 — 부분적으로 "시뮬레이터가 만든 것만" 구분해서
  지우는 기능은 만들지 않는다. `detected_events`/`completed_events`에는 이벤트가
  어디서 발생했는지 구분할 컬럼이 없어서, 구분하려면 스키마 변경이 필요하고 이번
  스코프에서는 그 비용이 정당화되지 않는다고 판단)
- 원본 `telemetry`/`errors`/`failures`/`maint`는 건드리지 않는다(읽기 전용 유지).

**`GET /simulator/status`에 `has_stale_events` 필드 추가**: `sim_state`가 전부
HEALTHY인데 `detected_events`에 행이 있으면 `true` — "지금 보이는 이벤트는 시뮬레이터가
만든 게 아니라 이전 데이터"라는 신호. UI가 이 값을 보고 "리셋 후 시작하시겠습니까?"
안내를 띄울 수 있다(UI 단계에서 구현).

**README/운영 절차**: 시뮬레이터를 처음 켜기 전에 `/simulator/reset`을 한 번 호출하는
것을 표준 절차로 문서화한다(README 또는 이 파일에 "시작하기 전" 체크리스트로).

## UI

- 이상감지 탭: 이벤트 목록 주기적 자동 갱신(스캔 버튼은 보조로 유지).
- **시뮬레이터 상태 패널**(이상감지 탭 상단):
  - 요약: 실행 중/정지, 시뮬레이션 시각, 속도, 시작/정지 버튼
  - 열화 진행 목록: 설비 번호, 신호, 방향, 상태, 진행률(경과 시간 ÷ 리드 시간), 현재 편차(σ), 발생한 전조 오류 수
  - 이벤트가 뜨기 전 열화 단계부터 보이게 한다.

## 성능

- 설비별 기준선(평균, 표준편차)을 원본에서 1회 계산해 저장·재사용(열화 데이터의
  기준선 오염 방지).
- `detect_anomaly()`가 전체 이력이 아니라 최근 구간만 읽도록 변경.
- 1분 = 1시간이면 하루 약 14만 행이 쌓이므로 `sim_telemetry` 보관 기간 제한(예: 최근 N일)을 둔다.

## 테스트 계획

- 상태 머신은 seed 고정으로 결정론적 단위 테스트(전이 순서, 고장은 06시에만 발생, 전조 오류 후 FAULT 전이, 스파이크 미감지).
- 통합 조회: 시뮬레이션 오류/고장이 `_diagnose_machine`에 반영되는지.
- 각 버그 수정과 같은 방식으로, 수정 전 코드로 되돌렸을 때 테스트가 실패하는지 확인.
- (2026-10-01) 서명 오류 시점·종류·조용한 고장 비율, 배경 오류율, 신호별 방향·크기, 부품별 나이 하한, 정비 사건 과정(초기 나이·정기 정비·고장 동반 정비), 연 고장 수 보정, `inject()` 방향, `hours_until_failure`, 오류 이력 30일 창, 틱의 락 안 읽기, `ml/sim_alarm_eval.py` 계산을 테스트로 고정(변이 검증 포함).

## 버그 수정: 시뮬레이션 시각이 원본 데이터셋 끝(2016-01-01)에서 이어받던 문제 (2026-09-22)

**증상 (사용자 실브라우저 테스트로 발견)**: "지금 전체 스캔하기"를 누르면 실시간 시뮬레이터
탭엔 "열화 진행 중인 설비 없음"인데도 긴급 이벤트가 여러 건 떴다.

**원인 (컨테이너 실 DB로 직접 확인)**: `#15/#64/#90/#95`로 뜬 긴급 이벤트는 시뮬레이터가
만든 게 아니라 **원본 정적 데이터셋에 원래부터 있던 2015-12-31 고장 기록**이었다.
`_tick_once()`가 첫 틱의 기준 시각을 `sim_query.dataset_now()`(원본+시뮬레이션 통합
최신 시각)로 잡다 보니, 시뮬레이터의 "지금"이 원본 데이터셋 끝(2016-01-01) 바로
근처에서 시작 - `check_recent_failure(within_days=1)`이 그 근처에 파묻혀 있던 원본의
오래된 고장 기록들을 "방금 발생"으로 오인식해서 되살아났다. 사용자가 제안한 "시뮬레이션
시각을 원본 데이터셋 끝이 아니라 시작 시점의 실제 현재 시각으로" 라는 방향이 정확히
근본 원인을 짚었고, 그대로 적용하니 두 증상(옛날 이벤트 오탐 + 헷갈리는 2016년 시각
표시)이 한 번에 해결됨.

**수정**: `sim_query.py`에 `sim_only_now()`(시뮬레이션 데이터에만 국한된 최신 시각,
원본과 통합 안 함) 추가. `_tick_once()`의 기준 시각과 `status()`의 `sim_now` 표시를
`dataset_now()`(통합) 대신 이걸로 교체 - 리셋 후 첫 틱은 실제 현재 시각(시 단위 반올림)에서
시작하고, 이후 틱은 거기서부터 시간 단위로 전진. `event_store._dataset_now()`(완료
이벤트 재표면화 판단 등)는 통합 방식 그대로 유지 - 시뮬레이터가 실제 "오늘" 기준으로
도는 이상 더는 옛날 기록과 헷갈릴 일이 없음.

**검증**: 재빌드 후 실제 컨테이너로 reset → start → inject(#77) → 8회 폴링(총 2분).
`sim_now`이 2026-09-22 → 09-27로 실제 날짜대로 전진, 설비 여러 대(31/46/62/77/2/48)가
자연 발생으로 DEGRADING→FAULT→HEALTHY 순환. `/scan` 결과 4건 전부 `evidence_at`이
`2026-09-25...`(진짜 시뮬레이션 근거)이고, 원본 2015~2016년 고장 기록은 "최근 오류
이력" 참고 텍스트에만 섞여 나올 뿐 긴급/주의 판정에는 더 이상 관여하지 않음을 확인. (2026-10-01: 이 텍스트 혼입도 오류 이력 30일 창으로 해소)
