# P-1: 부품 교체 이력(`PdM_maint.csv`) 탐색 노트

> MRO Copilot M0 사전 준비. `mro-copilot-upgrade-plan.md` §6-2 수요 예측의 근거 데이터를
> 명령 실행으로 직접 검증한 기록. 아래 수치는 2026-09-25에 상위 모델이 의뢰한 M0
> 사전 점검에서 먼저 보고된 값이며, 이 노트에서 로컬 데이터로 재현해 확인했다.

## 데이터 개요

- 파일: `archive/PdM_maint.csv` — 부품 교체 이력. 컬럼: `datetime`, `machineID`, `comp`.
- 전체 3,286건 (헤더 제외).
- 기간: 2014-06-01 06:00:00 ~ 2016-01-01 06:00:00.
- 대조 파일: `archive/PdM_failures.csv` — 실제 고장 기록. 컬럼: `datetime`, `machineID`,
  `failure`(=comp). 전체 761건.

## 1. 텔레메트리 수집 기간보다 앞선 기록

```
연도별 건수:
2014    400
2015   2879
2016      7
```

2014년 400건은 텔레메트리 수집 기간(2015-01 ~)보다 앞선다. 이 400건은 부품별 위험도
모델(U1)의 피처 공간과 대응시킬 텔레메트리가 없으므로, 수요 예측의 교체율 계산에서
**제외**한다.

## 2. 학습/테스트 기간별 부품(comp)별 건수

```python
train = maint[(maint['datetime'] >= '2015-01-01') & (maint['datetime'] < '2015-09-01')]
test  = maint[(maint['datetime'] >= '2015-11-01') & (maint['datetime'] < '2016-01-01')]
```

| comp | 학습기간(1~8월) | 테스트기간(11~12월) |
|---|---|---|
| comp1 | 464 | 122 |
| comp2 | 510 | 124 |
| comp3 | 469 | 125 |
| comp4 | 473 | 116 |

**결정**: 교체율은 학습기간(1~8월) 데이터로만 계산한다(U1 모델의 학습 기간과 동일 —
`uptime-update-plan.md`가 U1에 적용한 시간 기반 분할 원칙을 그대로 따름, 평가 누수
방지). 테스트기간(11~12월) 실제 건수는 수요 예측의 정확도를 평가하는 정답으로만
쓰고, 교체율 산출에는 절대 섞지 않는다.

## 3. 고장 후 교체 vs 예방 교체 — 이중 계산 위험 확인

전체 3,286건 중, **같은 시각·같은 설비·같은 부품**으로 `PdM_failures.csv`와 일치하는
건수(=고장 나서 교체된 건):

```python
merged = maint.merge(
    fail.rename(columns={"failure": "comp"}),
    on=["datetime", "machineID", "comp"], how="inner",
)
len(merged)  # 743
```

**주의(직접 확인 과정에서 발견)**: 처음에는 `datetime`+`machineID`만으로 병합했더니
1,104건이 나왔다 — 실제보다 361건 많다. 원인은 한 번의 정비 방문에서 여러 부품이
동시에 교체되는 경우, 그 방문의 모든 교체 건이 그 시각의 고장 1건과 매칭돼 중복
집계됐기 때문이다. **부품(comp) 일치까지 요구**해야 정확한 743건이 나온다 — 수요
예측 코드를 짤 때도 이 조건을 빠뜨리면 같은 함정에 빠진다.

743 / 3,286 = **22.6%**가 고장 후 교체다. 나머지 77.4%(2,543건)는 예방적 교체로
추정한다(정기 점검·계획 정비 등, 이 데이터셋에는 교체 사유 컬럼이 없어 "고장 기록과
매칭 안 됨"을 예방 교체의 대리 지표로 쓴다 — 이 가정은 합성 데이터 특성상 성립하지만
실제 도메인 데이터라면 별도 검증이 필요하다는 점을 명시해둔다).

## 4. 수요 예측 설계에 대한 결론

교체율(위 §2 학습기간 수치)에는 이미 고장 후 교체가 22.6% 섞여 있다. 여기에 "위험도
≥ 임계값인 설비 수"만큼 추가로 가산하면, 같은 고장 위험을 두 번 세는 것과 같다
(CP-M1 체크포인트 질문과 정확히 겹침).

**M1 착수 시 적용할 설계(2026-09-25 시점 — 이후 두 차례 더 수정됨, 최종 형태는
`mro-copilot-upgrade-plan.md` §6-2 참고)**:
1. 기본 수요 = 부품별 **예방 교체율**(전체 교체율에서 고장 후 교체를 뺀 나머지)만으로
   산출.
2. 위험도 가산 = "현재 위험도 ≥ 임계값인 설비 수" × "그 위험도 구간에서 실제로
   고장 후 교체가 발생한 비율"(학습기간 데이터에서 실측). 즉 고장 후 교체를
   기본 수요에서 완전히 빼고, 위험도 가산 항목 하나로만 반영한다.
3. 이 분리 방식과 실측 비율은 M1 착수 시 `docs/decisions.md`에 별도 기록한다.

**실제로는 이 설계 그대로 구현되지 않았다** — M1 착수 후 두 단계를 더 거쳤다:
(a) 2026-09-27 교차 검토에서 "위험도 가산"을 현재 시점 경보 설비 수로만 계산하면
30/90일 창의 대부분을 놓친다는 창(window) 불일치가 발견됐고, (b) 2026-09-28에는
그 수정안조차 검증기간 조건부 비율을 예측 창 전체에 적용해 22~32% 과소예측을 냈다.
최종적으로는 **1일차(오늘, 알람 상태를 아는 날)와 2일차 이후(미래, 모르는 날)를
분리**하는 형태로 정착했다. 이 문서의 §4는 최초 설계 의도(예방/고장 분리, 이중
계산 방지의 필요성)를 보여주는 기록으로만 유효하고, 정확한 계산식은
`mro-copilot-upgrade-plan.md` §6-2와 `backend/data/demand_forecast.py`의
`_expected_demand()`를 따른다.
