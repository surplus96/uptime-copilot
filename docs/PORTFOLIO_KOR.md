## 01 · Overview — 무엇을, 왜 만들었나

Azure Predictive Maintenance 데이터셋(설비 100대, 텔레메트리 약 87만 행, 오류/정비/고장
이력 포함)을 기반으로, "설비에 이상이 생기면 근거를 갖고 진단하고, 조치가 필요하면
승인을 거쳐 실제 현장 도구(Slack, CMMS)까지 연결되는" 코파일럿을 목표로 했습니다.

> **핵심 설계 원칙 — "사실은 코드가 말하고, LLM은 해석만 한다."**
> 진단 근거와 표준 조치 절차는 전부 결정론적으로 DB/코드에서 조회하고, LLM은 라우팅·
> 요약·관점 평가처럼 판단이 필요한 부분에만 관여합니다. 작업지시서 문구를 LLM이 다시
> 서술하지 않으므로 구조적으로 사실 왜곡(hallucination)이 끼어들 자리가 없습니다.

## 02 · Architecture — 시스템 아키텍처

Streamlit 프론트엔드가 FastAPI 백엔드를 호출하고, 모든 모델 입출력은 Harness(결정론적
검증 계층)를 거쳐 LangGraph 슈퍼바이저와 RAG 서비스로 위임됩니다. 상태는 SQLite, 문서
임베딩은 Chroma에 저장되며, 승인된 긴급 건은 Slack과 Atlas CMMS(MCP)로 전파되고
백그라운드 스캔은 새로 감지한 이상도 Slack에 올립니다.

## 03 · Core Logic

### 3단계 긴급도 판정

진단은 항상 아래 세 등급 중 하나로 귀결되고, 등급에 따라 그래프의 경로가 달라집니다.

| 등급 | 판정 근거 | 후속 동작 |
|---|---|---|
| 🟢 **일반** (normal) | 이상 징후 없음 | 바로 답변, 별도 조치 없음 |
| 🟡 **주의** (caution) | 고장 위험 모델 경보(학습된 모델이 없을 때만 Z-score로 대체) — 아직 확정 고장은 아님 | 작업지시서 생성 후 바로 확정 (승인 불필요) |
| 🔴 **긴급** (urgent) | `PdM_failures.csv`에 실제 로그된 고장 기록 존재 | 안전/생산/정비 3-관점 병렬 평가 → **HITL 승인 대기** → 승인 시 Slack + CMMS 전파 |

### LangGraph 멀티에이전트 그래프

`StateGraph` 하나로 라우팅부터 승인까지 관리합니다. 긴급 건만 3개 관점 노드를 병렬
실행하고 `interrupt()`로 멈춰 사람의 결정을 기다리며, 이 승인 상태는 SqliteSaver로
체크포인트되어 서버 재시작에도 살아남습니다.

```mermaid
flowchart TD
    START(("START")) --> route["route"]
    route -- "오류_진단" --> diagnosis["diagnosis"]
    route -- "정비_일정" --> schedule["schedule"] --> ENDs(("END"))
    route -- "일반_문의" --> general["general"] --> ENDg(("END"))
    diagnosis -- "일반 / 미등록 설비" --> finalize0["finalize"] --> ENDg2(("END"))
    diagnosis -- "주의 / 긴급" --> manual["manual_lookup"]
    manual --> parts["parts_check<br/>(MRO 확장)"]
    parts -- "주의" --> wo["work_order"]
    parts -- "긴급" --> safety["safety"]
    parts -- "긴급" --> production["production"]
    parts -- "긴급" --> maintenance["maintenance"]
    safety --> merge["merge_perspectives"]
    production --> merge
    maintenance --> merge
    merge --> priority["priority_rule"]
    priority --> wo
    wo --> validate["validate_work_order"]
    validate -- "긴급" --> approval[["approval\n(HITL interrupt)"]]
    validate -- "주의" --> finalize["finalize"]
    approval --> finalize
    finalize --> ENDf(("END"))
```
*그림 2 — 노드/엣지는 `backend/agent/agent_service.py`와 1:1 대응. `parts_check`는
`manual_lookup` 바로 뒤, 긴급/주의 분기 전에 있습니다 — 두 경로 모두 이 정보가 필요합니다.*

### RAG · Harness

| 구성요소 | 내용 |
|---|---|
| RAG 검색 | BM25(sparse) + Dense 임베딩 하이브리드 검색. 임베딩 모델은 `intfloat/multilingual-e5-small`, 벡터 저장소는 Chroma. Multi-Query 재작성과 Self-RAG 필요성 판단은 2026-09-23에 제거 — 이 코퍼스 규모에는 둘 다 과잉이었습니다. |
| Faithfulness 채점 | 답변 생성 후 컨텍스트 대비 사실 충실도를 LLM-judge로 자동 채점 (RAG 특유의 "그럴듯하지만 근거 없는 답변" 대응). |
| Harness | 결정론적 검증 계층. 입력 길이 검사, 출력에 대한 정규식 PII 체크(계산적), RAG 답변에 한정한 LLM-judge 충실도 체크(추론적). |

### 이벤트 스캐너 — 근거 기반 억제 로직

`/scan`은 LLM 없이 100대 설비를 전부 훑어 긴급/주의 건을 저장합니다. 완료 처리된
이벤트의 재감지 여부는 **벽시계 시간이 아니라 새로운 "근거"가 나왔는지**로 판단합니다 —
완료 시점 이후 새 오류 로그가 실제로 쌓여야만 다시 표면화됩니다.

## 04 · 자동 열화 시뮬레이터 (Automated Degradation Simulator)

원본 데이터셋은 2016-01-01에 멈춰 있어서, 누군가 수동으로 시계를 돌리지 않는 한 아무
일도 일어나지 않습니다. 그래서 설비별 상태 머신을 돌려 스스로 새 고장을 만들어내는
백그라운드 시뮬레이터를 만들었고, 진단 → 승인 → 알림 파이프라인이 사람 개입 없이 라이브
데모 동안 스스로 돌아갑니다.

```mermaid
stateDiagram-v2
    [*] --> HEALTHY
    HEALTHY --> DEGRADING: 발생 (시간당 확률)
    DEGRADING --> FAULT: 전조 오류 발생
    FAULT --> HEALTHY: 리드타임 경과 — 고장 + 정비 기록 생성
```
*그림 3 — `backend/data/sim_engine.py`가 구동하는 설비별 열화 생애주기*

> **추측이 아니라 실측 통계로 캘리브레이션.** 처음에는 임의 값을 썼습니다. 실제
> 데이터셋(설비 100대, 고장 761건)을 측정해서 모든 상수를 다시 세웠습니다 — 고장 시점
> 텔레메트리 편차는 가정했던 6σ가 아니라 평균 **1.6σ**, 리드타임은 **44~52시간**, 고장
> 대부분은 전 주에 어떤 오류든 선행하지만 오류 중 실제 고장으로 이어지는 비율은
> 소수입니다. 시뮬레이터는 이 통계적 질감을 그대로 재현합니다.

`asyncio` 백그라운드 태스크 하나가 설비 100대를 동시에 진행시키고(실제 1분 ≈ 시뮬레이션
1시간), 원본과 분리된 전용 `sim_*` 테이블에 기록하며, 매 틱마다 증분 스캔과 배치 Slack
알림을 실행합니다. `threading.Lock`으로 각 틱을 운영자 동작(강제 주입, 리셋)과
직렬화합니다.

## 05 · 고장 위험 예측 — 부풀려진 데모 신호에 맞춰진 임계값을 교체하다

시뮬레이터(§04)는 데모를 위해 고장을 눈에 띄게 만드는 장치입니다. 앱이 실제로 쓰는 탐지
로직(3σ Z-score 임계값)이 인위적으로 부풀리지 않은 데이터에서도 뭔가를 잡아내는지는
별개 질문입니다. 실측 결과, 실제 열화 중 3σ를 넘는 비율은 약 1.2%뿐이었습니다(데모의
부풀린 버전은 15%) — 임계값 자체가 틀린 게 아니라 데이터셋이 좀처럼 만들지 않는 강도의
신호에 맞춰져 있었던 겁니다.

그래서 부품별 LightGBM 분류기 4개를 만들어, 엄격한 시간 기준 분할로 학습·평가했습니다
(무작위 분할은 인접 3시간 표본끼리 피처가 겹쳐서 누수가 됩니다 — 아래 교차 검토에서 확인).

| 부품 | 이벤트 재현율 (모델) | 이벤트 재현율 (Z-score 기준선) | 3h 표본당 정밀도 (모델) | 3h 표본당 정밀도 (기준선) |
|---|---|---|---|---|
| comp1 | 100% | 73.3% | 96.7% | 17.5% |
| comp2 | 100% | 86.7% | 100.0% | 14.3% |
| comp3 | 100% | 100.0% | 99.3% | 6.0% |
| comp4 | 100% | 96.2% | 99.5% | 9.6% |

*이벤트 재현율 = 학습에서 전혀 보지 않은 11~12월 구간에서, 실제 고장 24시간 전 안에
모델이 한 번이라도 경보를 냈는가. 정밀도 = 양성 표시한 3시간 표본 중 실제로 고장 직전
구간이었던 비율.*

**이벤트 재현율만 보면 기준선도 나쁘지 않습니다** — 73~100%, comp3는 동점입니다. 진짜
격차는 정밀도입니다: 기준선의 개별 경보는 82~94%가 오탐인 반면 모델은 0~3.3%, 평균
조기경보시간은 19.5~21.0h입니다. "기준선은 아무것도 못 잡는다"가 아니라 "기준선은 진짜
신호를 오탐 속에 파묻고, 모델은 그렇지 않다"가 실제 주장입니다.

**별개로**, 데모-대-실제 격차를 아카이브 데이터가 아니라 시뮬레이터 자체로도 독립
재확인했습니다(Z-score 임계값만 보는 검증). "강한 에피소드" 손잡이(`STRONG_FRACTION`)를
끄고 8,760시간 × 설비 100대를 몬테카를로로 돌렸습니다:

| 모드 | `STRONG_FRACTION` | Z-score 탐지율 |
|---|---|---|
| 데모(기존 기본값) | 0.15 | 15.45% |
| 실측 수준으로 낮춤 | 0 | 0.00% |

0%는 설계상 정확한 값이고(정상 열화는 3σ 아래로 묶임), 아카이브 실측 예측치(약 1.2%)와도
일치합니다.

> **한계:** 이 정도로 거의 완벽한 수치는 실무 예지보전 모델에서 흔치 않습니다. 교차
> 검토로 데이터 누수는 배제했고, 이 공개 데이터셋이 실제 현장 데이터보다 쉬운 벤치마크일
> 가능성이 유력한 설명입니다. 노이즈 많은 실제 센서 데이터에 그대로 옮겨진다고 기대해서는
> 안 됩니다 — 전체 논의는 `docs/model_card.md` 8절 참고.

## 06 · External Integrations — Slack 알림 · CMMS 작업지시서 (MCP)

승인 이후의 알림/작업지시서 생성은 에이전트가 그때그때 판단하는 도구 호출이 아니라 이미
결정이 끝난 뒤의 고정 동작입니다. 그래서 도구 선택을 LLM에 맡기는
`langchain-mcp-adapters` 대신, MCP Python SDK로 정해진 도구(`create-work-order`)를 코드가
직접 결정론적으로 호출합니다.

> **Atlas CMMS**를 Docker Compose로 셀프호스팅하고, 커뮤니티 MCP 서버(Atlas-MCP)를 포크해
> 하드닝했습니다 — Bearer 토큰 상시 검사, 상수시간 비교, DNS 리바인딩을 막는 Host-헤더
> 화이트리스트. 이 패턴은 uptime-copilot 백엔드 자체의 `TrustedHostMiddleware`에도
> 재사용했습니다.

## 09 · LLM 제공자 유연성

`LLM_PROVIDER=ollama`로 바꾸면 라우팅·추출·관점 평가·RAG 판정까지 모든 LLM 호출이 코드
수정 없이 완전 로컬 모델로 전환됩니다. 이 전환의 비용을 직접 측정했고, 첫 측정이 공정하지
않았다는 걸 발표 전에 스스로 잡아냈습니다 — 초기 버전은 안전장치를 거치지 않은 클라우드
1회와 로컬 1회를 비교했습니다. 아래는 재측정한 수치입니다: 클라우드는 현재 코드로 1회,
로컬은 5회, 둘 다 안전장치 제작에 쓴 40문항과 한 번도 안 본 10문항 홀드아웃으로 나눠서
측정했습니다.

| 지표 | 클라우드(1회) | 로컬 Qwen3-8B(5회) |
|---|---|---|
| 라우터 정확도(40문항 골든셋) | 90.0% | 87.5~92.5% (평균 91.0%) |
| 라우터 정확도(10문항 홀드아웃) | 100.0% | 90~100% (평균 96.0%) |
| 설비번호 추출 / 번호 없을 때 되묻기 | 100.0% / 100.0% | 100.0% / 100.0% |
| 위험한 오분류(실제 설비 → 근거 없는 노드) | 0 | 0 (10회 전체) |
| 호출당 평균 지연 | ~1.2초 | ~13초 |

(로컬: Apple Silicon의 Qwen3-8B, Metal 외 GPU 가속 없음. 16GB 통합 메모리가 Docker
Desktop과 이 앱 자체 컨테이너만으로도 이미 빠듯하며, 메모리 압박 시 가끔 나오는 ~40초
이상치의 유력한 원인입니다.)

추출과 되묻기는 처음부터 클라우드와 같았습니다 - 폭이 좁고 형태가 고정된 작업입니다.
라우팅은 처음엔 두 자릿수 격차로 뒤졌고 별도 호출 두 번이라 약 10배 느렸는데, 둘 다 코드
쪽에서 좁혔습니다 - 라우팅+추출을 구조화 출력 하나로 합치고, 로컬 모델이 자주 잘못 보내는
표현을 잡는 결정론적 후처리를 추가했습니다. 골든셋 밖 스팟 체크에서 로컬 모델이 내부
모순된 출력(`risk_level: 중간`인데 `requires_shutdown: true`)을 낸 것도 발견해,
`requires_shutdown`을 코드에서 유도하도록 구조적으로 고쳤습니다. 결론: 로컬이 이제
정확도에서 클라우드와 같은 범위(91.0% vs 90.0%)이고 위험한 오분류는 0건입니다. 남은
비용은 지연이고, 호출 병합과 워밍업으로 완화되지만 없어지진 않습니다. 폐쇄망 배포라면
감수할 가치가 있고, 대가 없는 업그레이드는 아닙니다.

## 11 · MRO 확장 — 부품·재고와 보안 운영

예지보전 코어는 "이 설비가 고장 나고 있는가?"에 답합니다. 실제 MRO(정비·수리·운영)

새어나가지 않는다는 증명과 무슨 일이 있었는지의 기록도 필요합니다. 부품 마스터 자체(부품번호·
재고·리드타임·단종일)는 전부 합성값이며 화면과 `docs/design/parts_assumptions.md`에 그렇게
명시돼 있습니다. 수요 예측의 교체율과 백테스트(아래)는 §05와 마찬가지로 실제 Azure PdM
데이터로 계산됩니다. 왜 별도 확장으로 다루는지는
[mro-copilot-upgrade-plan.md](../mro-copilot-upgrade-plan.md) §0-1 참고.

| 구성요소 | 내용 |
|---|---|
| 부품 마스터 + 수요 예측 | 합성 부품 5개, 30/90일 교체 수요를 예방 항과 고장 항으로 분리 예측, 실제 2015년 11~12월 교체 건수 대비 백테스트 오차 -5.0%~+3.5% (기본 교체율을 검증할 뿐, 경보 항은 ~120건 중 0~2건만 더함) |
| 재고 위험 대시보드 | `GET /parts/inventory_risk` - 진짜 위험(리드타임이 예측 기간보다 김)과 정상 재주문 신호를 구분 |
| 우선순위와 분리된 조달 긴급도 | 부품이 없다고 진단이 더 급해지지 않음 - 백그라운드 스캐너와 같은 결정론 함수가 판단하는 작업지시서의 별도 줄 |
| 오프라인 모드 | 기동·CMMS 호출 시점에 검증하는 설정된 엔드포인트 허용 목록 - 알 수 없는 `OFFLINE` 값·안전하지 않은 제공자·허용 목록 밖 엔드포인트·모호한 URL·우회 프록시가 있으면 기동을 거부하고, 다른 무엇보다 먼저 `HF_HUB_OFFLINE` 강제·트레이싱 비활성화를 적용(`main.py` 진입점에 한해 성립). CI는 *LLM과 진단 모두 스텁으로 대체한* 진단→승인 시나리오에 `pytest-socket`을 실행. **증명하지 못한 것**: 프록시·DNS·리다이렉트 경로(프록시는 대신 기동 시점에 거부), CI가 실행하지 않는 기동·RAG 초기화(따로 확인) |
| 감사 로그 | LLM을 쓰는 모든 단계(실패 포함)·부품 조회·승인/반려·Slack/CMMS 전송을 실제 결과와 함께 스레드ID로 상관하며, 재시도한 호출과 RAG 답변+판정은 각각 한 행으로 남습니다. **기록하지 않는 것**: 진단용 데이터 조회와 백그라운드 스캔의 부품 조회. 자유 텍스트는 패턴으로만 개인정보를 마스킹(이름·주소는 불가) |

것처럼 보이지만 아닙니다 - `disable_socket()`은 `socket.socket` 자체를 교체하고
`getaddrinfo`를 무조건 막아서, `socket_allow_hosts()`의 허용 목록 검사가 실행되기도 전에
끝나버립니다. 플러그인 소스를 직접 읽어보니 실제 지원 조합은 `allow_hosts` 마커
하나뿐이었고, 그걸로 바꾸자 허용 목록 테스트가 맞는 이유로 통과하기 시작했습니다.
</details>

<details>
<summary><strong>GAP · 가장 안전과 관련 있는 로그 줄에 스레드ID가 없었다</strong></summary>

감사 로그 연결 지점 6곳을 붙인 뒤 스레드ID로 필터링해 실제 시나리오를 돌려봤더니
안전/생산/정비 3관점 평가가 통째로 빠져 있었습니다. 이 평가를 공유하는 함수가 애초에
`thread_id`를 받지 않았기 때문입니다. "연결 지점 6곳이면 로그 6줄"을 믿는 대신 실제
시나리오를 끝까지 조회해본 것이 이 갭을 드러낸 방법입니다.
</details>

<details>
<summary><strong>WAR STORY · "테스트로 증명됨"과 "강제됨"은 서로 다른 주장이었다</strong></summary>

이 섹션을 쓰기 전 M2 마일스톤 전체를 자체 판정하지 않고 교차 검토로 보냈습니다. 검토
결과: 오프라인 가드의 DoD("외부 호출 0회, 증명됨")는 테스트 범위에서는 맞았지만 런타임에는
대응하는 강제가 없었습니다 - `LLM_PROVIDER=Ollama`(대문자 하나 다름)는 대소문자 비교를
조용히 통과해 실제로는 OpenAI API로 연결됐고, `cmms_client.py`는 허용 목록을 아예
참조하지 않았으며, `HF_HUB_OFFLINE`은 어디에도 세팅된 적이 없었습니다. 별개로 감사 로그의
"모든 호출이 기록된다"는 주장도 존재하는 연결 지점에서는 맞았지만,
`cmms_client.push_work_order()`는 성공·미설정·차단 세 경우 모두 `None`을 반환했고 기록
코드는 셋 다 "성공"으로 취급했습니다. 아무것도 고치기 전 전부 실제 컨테이너에서 재현했고,
런타임 강제·감사 정확성·이 섹션의 문서 주장을 고쳤습니다 - 고치는 과정에서 이 케이스
스터디 자체의 오류 2건도 더 찾았습니다(2026-09-23에 제거된 Multi-Query가 문서 8곳에
남아있던 것, "아래 수치는 전부 합성"이라는 이 섹션의 문구가 실제로는 §05처럼 실데이터
백테스트를 포함하고 있던 것). 전체 기록은 `docs/decisions.md`에 있습니다.
</details>
