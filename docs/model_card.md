# 고장 위험 예측 모델 — 모델 카드

> 작성일 2026-09-23 · `uptime-update-plan.md` U1(③) 산출물 · 재현: `backend/ml/build_features.py` → `backend/ml/train.py`

## 1. 무엇을 예측하는가

설비 × 시각(3시간 간격 샘플) 별로, **향후 24시간 이내에 부품 X(comp1~4)가 고장날지** 예측하는 이진 분류기 4개(부품별로 독립).

기존 `detect_anomaly()`(Z-score, 임계값 3σ)는 실측 결과 '주의' 탐지 재현율이 사실상 거의 안 나오는 상태였다(`docs/model_exploration.md`) — 이 모델은 그 자리를 대체·보강한다.

## 2. 데이터

- Azure Predictive Maintenance 공개 데이터셋(`archive/PdM_*.csv`), 설비 100대, 2015-01-01 06:00 ~ 2016-01-01 06:00.
- 텔레메트리 87.6만 행(설비당 정확히 8,760행, 결측 없음), 고장 761건, 오류 3,919건, 정비 3,286건.
- 상세 분포·실측 통계는 `docs/model_exploration.md` 참고.

## 3. 라벨·피처 정의

| 항목 | 정의 |
|---|---|
| 라벨 | `(T, T+24h]` 구간에 해당 부품 고장이 있으면 1 |
| 텔레메트리 피처 | 4개 신호(volt/rotate/pressure/vibration) × 3h·24h 이동평균·표준편차 |
| 오류 피처 | 5개 오류 유형 × **24h+48h 이중 창** 카운트 |
| 정비 피처 | 부품별 마지막 정비 후 경과시간(시간 단위) |
| 메타 피처 | 설비 모델(범주형), 사용연수 |
| 표본 | 3시간 간격, 설비별 관측 시작 직후(오류 48h 창이 덜 찬 구간)와 관측 끝 직전(라벨 24h 창이 데이터 밖으로 나가는 구간) 제외 |

**오류 피처가 24h+48h 이중 창인 이유**: 3-1 탐색에서 선행 오류가 고장 24~36시간 전에 98% 몰려 있음을 실측(8.5%@24h → 98%@36h, `docs/model_exploration.md` 3절) — 24h 창 하나로는 가장 강한 신호를 놓친다. `docs/decisions.md` 2026-09-23 항목에 결정 기록.

## 4. 분할

시간 기준: 1~8월 학습(train, 192,600행) / 9~10월 검증(val, 48,800행) / 11~12월 테스트(test, 48,300행). 설비 기준(무작위) 분할은 **쓰지 않음** — 3시간 간격 샘플에 24~48시간 피처 창이 겹쳐서 인접 행끼리 피처가 거의 동일하므로, 무작위/행 단위 분할은 누수가 된다(CP-U1 교차 검토 지적, `docs/decisions.md` 참고).

## 5. 모델

- LightGBM(`LGBMClassifier`), `n_estimators=200, learning_rate=0.05, num_leaves=15, is_unbalance=True`. 부품별로 독립 학습.
- 범주형 피처(설비 모델)는 LightGBM 네이티브 처리(pandas category dtype).
- 클래스 불균형(양성 약 0.5%)은 `is_unbalance=True`로 대응, 별도 다운샘플링 없음.

## 7. 임계값

기본 임계값 `0.5`(튜닝 없음)에서 이미 설비당 하루 오경보 ≤0.001건으로, 계획서가 제시한 "설비당 하루 오경보 ≤ N건" 제약을 여유 있게 만족한다. 재현율도 이미 0.99~1.00이라 임계값을 더 낮춰 재현율을 올릴 실익이 없다 — 이번 버전은 **임계값 튜닝을 생략**했다. 오경보 예산을 늘려도 되는 배포 환경이라면 임계값을 낮춰 조기경보시간을 더 벌 수 있다(미실험).

## 8. 한계 · 주의사항 — 반드시 읽을 것

1. **실측치가 이례적으로 높다.** 재현율/정밀도/PR-AUC가 거의 1.0에 가까운 건 실무 PdM 모델에서 매우 드물다. CP-U1 교차 검토(상위 모델, `docs/decisions.md` 2026-09-23)로 미래 데이터 참조 누수는 없음을 확인했고, 행 단위·이벤트 단위 지표가 같은 방향으로 일치해 행 중복에 의한 착시도 아님을 확인했다. **잠정 결론은 Azure PdM 합성 데이터셋 자체가 깨끗하게 주입된 열화 패턴을 갖고 있어서라는 것**이다 — 실제 현장의 노이즈 많은 센서 데이터에 이 정도로 깨끗하게 일반화된다고 가정해서는 안 된다.
2. **고장 원인의 생성 과정을 모른다.** 이 데이터셋이 어떻게 합성되었는지 원 저작자의 상세 스펙이 공개되어 있지 않아, "왜 이렇게 잘 분리되는가"를 코드 바깥에서 완전히 검증할 방법이 없다.
3. **설비 2대는 테스트 대상에서 사실상 제외.** 100대 중 2대는 고장 이력이 아예 없어 학습 신호가 없다.
4. **클래스 불균형이 크다** (양성 약 0.5%) — `is_unbalance=True`만으로 대응했고, threshold 이동/코스트-센서티브 러닝 등은 시도하지 않았다.
5. **온라인(실시간) 재학습 없음.** 이 모델은 정적 스냅샷 학습 결과이며, `backend/store/ml_features/`에 캐시된 피처를 재사용한다. 배포 후 실데이터 분포가 바뀌면(예: 새 설비 모델 추가) 재학습이 필요하다.
6. **메모리**: 전체 피처 테이블 292K행 × 38열, float32/int16 기준 약 36MB — 16GB RAM 환경에서 전혀 부담 없음. 학습 자체도 수 초~수십 초 내 완료.

## 9. 현실화 모드 비교 — 데모가 실제보다 쉬워 보이는 이유

`backend/data/sim_engine.py`의 `STRONG_FRACTION=0.15`은 데모에서 열화가 눈에 띄게 하려고
넣은 값이다 — 실제로는 이런 강한 열화(3σ 이상)가 1.2%뿐인데, 데모는 15%로 부풀려 보여준다.
"실측 수준으로 낮춘 현실화 모드"(`STRONG_FRACTION=0`)에서 Z-score(3σ) 탐지율이 실제로 얼마나
떨어지는지, 몬테카를로로 직접 돌려서(8,760시간 × 설비 100대, `sim_engine.step()` 실제 코드
경로 그대로) 확인했다:

| 모드 | `STRONG_FRACTION` | 에피소드 수 | Z-score(3σ) 탐지율 | 모델 탐지율 |
|---|---|---|---|---|
| 데모(기존 기본값) | 0.15 | 712 | **15.45%** (실측) | 사실상 100%\* |
| 현실화(실측 수준) | 0 | 696 | **0.00%** (실측) | **100%**(6절 이벤트 재현율, 실측) |

\* 데모 모드는 강한 열화(3.2~4.5σ)를 인위적으로 섞은 것이라, 이미 더 약한 실제 신호(현실화
모드)를 100% 잡아내는 모델이 더 강한 신호를 놓칠 이유가 없다는 추론이다 — 별도로 측정하지
않았다(데모용 가짜 분포로 모델을 다시 학습·평가하는 건 의미가 없어서 생략).

`STRONG_FRACTION=0`일 때 Z-score가 정확히 0.00%인 이유는 우연이 아니라 설계다: 정상 열화는
`DRIFT_CLIP=(0.8, 2.6)`으로 항상 3σ 아래에 묶여 있고, 강한 열화만 `STRONG_RANGE=(3.2, 4.5)`로
항상 3σ 위에서 시작한다 — 둘 사이에 갭이 있어서 `STRONG_FRACTION`이 곧 Z-score 탐지율과
정확히 같아진다. 이게 바로 U1 전체의 출발점이었던 문제(`docs/model_exploration.md`, "실제
분포에서 '주의' 탐지 재현율은 약 1%")를 시뮬레이터 파라미터 수준에서 재확인한 것이다.
