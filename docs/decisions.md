## 2026-09-23 — 🔶 CP-U1 조기 발동: 3-3 학습 결과가 비정상적으로 좋아서 누수 의심

**배경**
3-3(학습+시간분할평가+Z-score 기준선 비교)에서 LightGBM 4개 부품 분류기의 재현율/정밀도/
PR-AUC가 0.94~1.00으로 나옴(Z-score 기준선은 0.05~0.5) — H2의 "결과가 너무 좋을 때" 트리거
발동, 3-4 완료 전에 CP-U1을 조기로 당겨서 상위 모델(사용자가 직접 전달) 교차 검토를 받음.

**지적 사항** (상위 모델 검토 결과)
- 피처 쪽 미래 데이터 참조 누수는 없음 — `build_features.py`의 텔레메트리/오류/정비 피처는
  전부 `(T-w, T]` 구간만 사용, 라벨만 `(T, T+24h]`로 미래를 봄(의도된 설계).
- 핵심 위험 지점이었던 "고장과 동시각 정비 기록"(761건 중 743건)은 라벨 경계가
  `T == 고장시각`인 행을 정확히 배제해서 이미 안전하게 처리되고 있었음을 실측으로 확인.
  (`lo` 쪽을 `side="left"`로 바꾸면 이 743건이 그대로 누수가 됐을 것 — 지금 방식 유지 필요)
- 시간 기준 분할(1~8월/9~10월/11~12월) 방식 자체는 올바름. 단, 3h 간격 샘플에 24~48h
  피처 창이 겹쳐서 인접 행끼리 피처가 거의 동일 — **무작위 행 분할은 절대 쓰면 안 됨**
  (지금처럼 시간 기준 또는 machineID GroupKFold만 안전).
- 마이너: (1) 설비별 초반 구간(오류 48h 창이 덜 찬 상태)이 필터 안 된 채 포함됨,
  (2) 데이터 끝부분 라벨이 관측 구간을 넘어갈 수 있는데 필터 없음(현재 데이터엔 영향 0),
  (3) 코드 주석이 "T 이전만"이라고 돼 있으나 실제론 T 포함 — `(T-w, T]`로 정정 필요.

**조치**
- `build_features.py`에 초반/끝 구간 필터 추가, 주석 정정 (다음 커밋에서 반영 예정).
- 높은 성능 자체(재현율/정밀도 ~1.0)는 누수로 확정되진 않았음 — 코드 경계는 검증됐고,
  Azure PdM 합성 데이터셋이 원래 잘 분리되는 특성으로 알려져 있다는 정황도 있음.

**미해결 항목 — 해소됨 (2026-09-23 추가 확인)**
- 3가지 수정(초반/끝 구간 필터, 주석) 반영 후 재학습해도 행 단위 지표는 거의 그대로
  (recall 0.99~1.00, precision 0.97~1.00) — 지적된 경계 문제가 원인이 아니었음을 재확인.
- "행 중복이 지표를 부풀리는가" 의심을 닫기 위해 이벤트 단위 지표(테스트 구간 실제 고장
  이벤트별로, 그 24h 이전 구간에서 한 번이라도 탐지했는지)를 별도 계산: 모델 이벤트
  재현율 1.0(4개 부품 전부), Z-score 기준선은 0.73~1.0. 행 단위와 이벤트 단위가 같은
  방향으로 일치해서, 행 중복에 의한 착시는 아님을 확인.
- 평균 조기경보시간 19.5~21.0시간, 설비당 하루 오경보 0.001건 이하 — 별도로 계산한
  이 두 지표도 "지나치게 좋다"는 인상과 일관됨.
- 결론: 코드 누수는 없고, 이 정도로 높은 성능은 Azure PdM 합성 데이터셋 자체의 특성
  (깨끗하게 주입된 열화 패턴)으로 잠정 결론. 다만 실제 현장 데이터에는 이 정도로
  깨끗하게 일반화되지 않을 수 있다는 caveat를 3-4 모델 카드에 명시하기로 함.

## 2026-09-23 — 🔶 CP-U2: priority_rule 규칙 설계 (4-2, 계획된 체크포인트)

**배경**
4-2(우선순위 P1~P3 + 정지 권고 규칙) 구현 전, 계획서가 명시한 체크포인트라 초안을
상위 모델(사용자가 직접 전달)에 검토받음.

**지적 사항** (상위 모델 검토 결과)
- **실측 근거**: 테스트 구간 전체를 4개 모델로 채점해보면, 긴급(최근 30일 내 실제 고장)
  행의 98%에서 위험도 확률이 0.01 미만이다 — 고장 직후 정비 기록이 생겨서
  `hours_since_maint`가 리셋되기 때문. 즉 긴급 케이스에서 모델은 "이 부품이 방금
  고쳐졌다"고 정확히 답하고 있을 뿐, "안전하다"는 뜻이 아닌데 초안 규칙은 이걸
  "낮은 위험"으로 잘못 해석하고 있었다.
- 모델 확률은 0.5~0.8 구간에 데이터가 전혀 없어(사실상 on/off 신호), `is_unbalance=True`라
  확률이 보정되지도 않음 — 0.5/0.8 두 임계값을 나누는 건 근거가 없다. 기존 `RISK_THRESHOLD`
  하나를 재사용해 on/off 경보로만 취급해야 한다.
- `requires_shutdown`은 모델 확률만으로 결정하면 안 된다(모델 카드 8절의 일반화 한계
  경고와 상충) — 정지 권고는 관점 판단에서만 나와야 하고, 모델 경보는 우선순위를
  올리는 "이유"로만 반영한다.
- `_DEFAULT_ASSESSMENT`(관점 평가 실패 시 대체값)에 실패 여부를 구분하는 플래그가 없어서,
  "정직하게 중간이라고 판단한 것"과 "평가 자체가 실패한 것"이 똑같이 보인다 — 후자가
  P3로 떨어지는 게 원래 지적 2번(관점 3개 다 실패 시 P3 문제)의 근본 원인.
- `high_risk_votes >= 2`(과반 투표) 방식은 부적절 — 3개 관점이 같은 모델·같은 입력에서
  프롬프트만 다르게 뽑힌 거라 "독립적인 3표"로 취급하면 안 된다. 관점별로 라벨링해서
  규칙을 짜야 한다(예: 안전 관점의 "높음"은 다른 관점이 반박해도 격하되면 안 됨).
- 승인자에게 "왜 이 우선순위인지" 이유가 안 보인다 — `priority_reasons` 같은 필드로
  근거를 노출해야 한다.

**조치**
- `_DEFAULT_ASSESSMENT`에 `is_fallback: True` 추가, 정상 평가는 `is_fallback: False`.
- `risk_probability`를 모델 미사용 시 `0.0`이 아니라 `None`으로 유지(누락과 "0%"를
  구분), `risk_component`(모델이 지목한 부품)도 같이 state에 추가.
- 규칙을 관점별 라벨링 + `RISK_THRESHOLD` 재사용 on/off 경보 + `priority_reasons` 포함하는
  구조로 재작성 (상위 모델이 제안한 구체 코드 반영).
- 유효한(비-fallback) 평가가 2개 미만이면 P2를 하한으로 하고 "판정 근거 부족" 사유를 남김
  — 별도 P0/미판정 등급은 만들지 않음(정렬 로직 단순하게 유지).

**미해결 항목**
- 동일 우선순위 내 정렬(고장 최근순 등)은 이 노드의 책임 범위 밖으로 남겨둠 — 여러 건을
  동시에 보여주는 화면(스캔 목록 등)이 생기면 그때 다룬다.

## 2026-09-23 — 5-1/5-2: RAG 역할 축소 (Multi-Query·Self-RAG 제거)

**지적 사항** (계획서 6-2 원안)
- 에이전트(`/agent/query`)는 RAG를 전혀 쓰지 않는다 — `manual_lookup_node`가
  `PUMP_MAINTENANCE_PROCEDURES`(코드에 이미 정확히 아는 데이터)를 직접 조회한다
  (`agent_service.py` 주석: "매뉴얼 문서가 작아 RAG 검색이 부품을 정밀하게
  구분하지 못하는 문제가 있어" 직접 조회로 전환했다는 기존 기록).
- `/rag/query`(순수 문서 Q&A 보조 기능)의 코퍼스는 생성된 txt 문서 몇 개 분량인데,
  그 규모에 Multi-Query(질문 재작성) + Self-RAG(검색 필요 여부 판단) + 하이브리드
  검색 3단 파이프라인이 얹혀 있었다 — 코퍼스 규모 대비 과잉설계.

**조치**
- Multi-Query 제거: `rag_service.py`에서 `MultiQueryRetriever` 래핑을 걷어내고
  하이브리드(Dense+BM25) 검색기를 그대로 사용.
- Self-RAG 제거: `main.py`의 `/rag/query`에서 `should_retrieve()` 분기(검색 필요
  여부를 LLM이 판단해서 아니면 일반 잡담으로 빠지는 경로)를 삭제 — 이 엔드포인트는
  이제 "매뉴얼 Q&A 보조 기능"으로 역할이 고정되고, 일반 잡담/설비 진단은
  각각 `/agent/query`의 `general_node`/`diagnosis_node`가 담당한다(역할 중복 제거).
  하이브리드 검색 + 충실도(faithfulness) 판정은 그대로 유지.
- 죽은 코드 정리: `should_retrieve()`, `RetrievalDecision`, `ROUTING_PROMPT_TEMPLATE`
  (`core/harness.py`)와 `core/prompts.py`(Self-RAG 분기에서만 쓰이던 일반 챗봇용
  `SYSTEM_PROMPT`) 전체 삭제 — 호출부가 0건이 됨.
- **RAG 역량을 축소하는 이유**: 이 코퍼스 규모에서 RAG 고급 기법(Multi-Query, Self-RAG)을
  시연하는 건 실익이 없고, RAG 역량 자체는 후속 프로젝트 SpecGuard(계획서 서두 참고)에서
  더 큰 코퍼스로 제대로 시연할 예정이라 여기서는 걷어낸다.

**미해결 항목**
- 없음 (제거 후 기존 테스트 전부 통과 확인: 빠른 경로 70개 + 무거운 RAG 재적재
  테스트 2개, `docs/decisions.md` 기록으로 종료)

## 2026-09-23 — 🔶 CP-U3: 케이스 스터디(docs/PORTFOLIO.md) 갱신 교차 검토

**배경**
U1/U2 작업을 반영한 케이스 스터디 새 섹션(§05 고장 위험 예측, 헤드라인 지표 교체)을
커밋하기 전, 계획서가 명시한 체크포인트라 상위 모델(사용자가 직접 전달) 교차 검토를 받음.

**지적 사항** (상위 모델 검토 결과 — 4개 질문보다 더 큰 문제 하나 포함)
- **실제 오류(가장 심각)**: 헤드라인 "100% vs 0% Z-score"가 서로 다른 두 실험을 하나의
  비교처럼 붙여놓았음. 100%는 원본 아카이브 테스트 구간(11~12월)에서 잰 모델의 이벤트
  재현율. 0%는 시뮬레이터를 `STRONG_FRACTION=0`으로 돌린 몬테카를로 결과인데, **모델은
  이 데이터로 평가된 적이 한 번도 없음**. `model_card.md` 9절의 "모델 100%"도 6절 수치를
  그대로 옮겨 적은 것이고 각주에 "별도로 측정하지 않았다"고 스스로 적어놓고도 표에서는
  나란히 비교한 것처럼 보이게 배치했었음. 같은 데이터로 비교하면 "100% vs 73~100%"임.
- 100% 단독으로도 경험 있는 독자에게는 경고 신호 — 헤드라인에 caveat 힌트가 필요.

**조치**

- "타임아웃 ≠ 실패"라는 패턴을 한 곳(승인 경로)에서 배웠다고 전체 앱에 자동으로
  퍼지지 않는다. 같은 원칙이 필요한 다른 경로(최초 질의)를 놓치기 쉬우므로, 이런 패턴을
  도입할 때는 "이 원칙이 필요한 다른 곳이 있는가"를 별도로 점검해야 함.

## 2026-09-25 — 로컬 LLM 성능 한계 돌파: 모순 필드 제거 + 골든셋 확장 + 호출 병합

**배경**
사용자에게 "로컬 LLM으로 계속 개선한다고 전제하면 앞으로 부딪칠 한계를 어떻게
돌파할지" 설명한 뒤, 그 제안한 우선순위 1~3번(4번 LoRA 파인튜닝은 보류)을 실제로
구현. 목표는 더 큰 모델이 아니라 코드 쪽 개입만으로 로컬 모델의 약점을 흡수하는 것.

**1) `requires_shutdown` 모순을 구조적으로 제거**
- `PerspectiveAssessment`에서 `requires_shutdown` 필드를 없앰. 대신
  `_derive_requires_shutdown(risk_level, recommended_window)`가
  `risk_level=="높음" and recommended_window=="즉시"`일 때만 True를 반환하도록
  코드가 결정론적으로 계산(`_assess_perspective`가 LLM 응답이든 실패 시 기본값이든
  항상 이 함수를 거치게 함).
- 기존엔 LLM이 세 필드(`risk_level`/`recommended_window`/`requires_shutdown`)를
  각각 독립적으로 채워서 "중간 위험인데 정지 필요" 같은 모순이 실제로 나왔다(9-23
  항목 참고). 이제는 그 필드를 LLM에게 아예 안 맡기므로 모순 자체가 발생 불가능.
  기존 LLM이 자유롭게 고르던 것보다 발동 조건이 좁아졌다(보수적) — 위험도/시점 둘
  다 최고 수준일 때만 정지 권고.
- `priority_rule_node`는 변경 없음 — 여전히 `p["requires_shutdown"]`를 읽을 뿐이라
  값의 출처가 바뀐 것만으로 하위 로직에 영향 없음.

**2) 골든셋 평가가 실제 코드 경로를 타도록 재설계 + 관점 평가 커버리지 추가**
- `test_golden_set_accuracy`가 라우팅 프롬프트를 따로 복제해서 부르던 걸
  `agent_service.route_node()`를 직접 호출하도록 변경 — 안전장치(정규식/키워드
  후처리)가 항상 포함된 상태로 측정되게 함. 이전 방식은 실제 배포 동작과 숫자가
  어긋날 수 있었음(실제로 어긋났었다 - route_node엔 안전장치가 있는데 이 테스트는
  그걸 안 거치고 있었음).
- 새 지표 `misroute_to_ungrounded`(오분류가 근거 없는 general_node로 착지하는
  케이스) 추가, 그 중에서도 `expected_machine_id`가 있는 케이스만 `dangerous_misroute`로
  분리해 무관용 회귀 어서션을 걺. 번호 없는 케이스(예: "설비가 이상해요")는 같은
  경로로 빠져도 특정 설비를 잘못 말할 대상 자체가 없어 심각도가 다르고, 이 문형은
  실행마다 LLM 판정이 흔들리는 것도 실측으로 확인돼서 무관용으로 걸면 flaky
  테스트가 됨 — 지표로만 남김.
- 관점 평가(안전/생산/정비)는 골든셋 범위 밖이라 지금까지 스팟 체크로만 문제가
  발견됐음(9-23, 9-25 항목). `test_perspective_assessment_consistency` 신규 추가:
  대표 진단 텍스트 3개 × 3관점 = 9건을 실행해서 예외 없이 파싱되는지, 그리고
  `requires_shutdown`이 위 1)의 유도 규칙과 항상 일치하는지(모순 불가능성 자체를
  검증) 확인. risk_level의 "정답"은 도메인 판단이 필요해 라벨링돼 있지 않으므로
  의미 품질 채점은 하지 않음 - 커버리지 스모크 테스트로 명시.

**3) 라우팅+추출 호출 병합 + Ollama 워밍업**
- `RouteDecision`에 `machine_id` 필드 추가, `route_node`가 분류와 설비번호 추출을
  한 번의 구조화 출력 호출로 처리. `diagnosis_node`/`schedule_node`는 더 이상
  `_extract_machine_id()`를 따로 호출하지 않고 `state.machine_id`(route_node가
  이미 채워둠)를 그대로 씀. `_extract_machine_id`/`IncidentExtraction`은 아무도
  안 써서 삭제(죽은 코드 방치 안 함).
- `main.py` lifespan에 `_warm_up_ollama()` 추가 - `LLM_PROVIDER=ollama`일 때만
  기동 직후 더미 호출 1회를 백그라운드 태스크로 보내 모델을 미리 로드. 헬스체크를
  막지 않게 fire-and-forget, 실패해도 무시.
- README(EN/KOR)에 호스트에서 `OLLAMA_KEEP_ALIVE=30m ollama serve`로 띄우라는
  운영 권장사항 추가(코드가 못 건드리는 영역 - Ollama는 호스트에서 도는 별도
  프로세스).

**실측 결과** (`LLM_PROVIDER=ollama .venv/bin/python -m pytest tests/eval/test_golden.py -m eval`)

  상승 - 병합 자체가 정확도에도 부수적으로 도움이 됨), 그런데 새 `misroute_to_ungrounded`
